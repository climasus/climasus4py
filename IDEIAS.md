## 2026-08-13 — sus_mod_spacetime_bayes / sus_mod_spatial_bayes (e 4 dependentes): stubadas por falta de porte fiel de INLA/CARBayes

- **O quê:** essas 6 funções do R dependem de dois pacotes sem equivalente Python:
  - `sus_mod_spacetime_bayes()` (modelo hierárquico Bayesiano espaço-tempo: priors espaciais BYM2/BYM/Besag/IID + priors temporais RW1/RW2/AR1 + interação Knorr-Held) e, para `model="bym2"`, parte de `sus_mod_spatial_bayes()`, dependem do **INLA** (`INLA::inla()`), cuja inferência por aproximação de Laplace integrada aninhada (INLA) não tem implementação em nenhuma biblioteca Python — não é uma questão de "reescrever a chamada", é um algoritmo de inferência sem porte disponível.

  - `sus_mod_spacetime_exceedance()`, `sus_mod_spacetime_predict()` e `sus_mod_plot_spacetime()` só operam sobre o objeto `climasus_spacetime_bayes` retornado por `sus_mod_spacetime_bayes()`; `sus_mod_plot_spatial_bayes()` só opera sobre o objeto `climasus_spatial_bayes` retornado por `sus_mod_spatial_bayes()`. Como nenhum desses objetos jamais existirá em Python (a função que os produziria sempre lança `NotImplementedError`), as 4 funções dependentes foram estubadas junto, mesmo sem chamar INLA/CARBayes diretamente.
  - Todas as 6 foram implementadas como stubs: assinatura pública completa (mesmos nomes/parâmetros/defaults do R, incluindo `lang`), docstring completa em estilo Google, e corpo que lança `NotImplementedError` imediatamente com a dependência bloqueadora nomeada na mensagem. Testes em `tests/test_mod_spacetime_bayes.py`, `test_mod_spatial_bayes.py`, `test_mod_spacetime_exceedance.py`, `test_mod_spacetime_predict.py`, `test_mod_plot_spacetime.py`, `test_mod_plot_spatial_bayes.py` confirmam o `NotImplementedError` com a dependência mencionada na mensagem.
- **Por que não agora:** decisão de escopo já validada com o usuário nesta rodada (estubar, não aproximar). Qualquer implementação futura por aproximação (ex.: BYM/CAR via PyMC com NUTS em vez de INLA/CARBayes) muda o algoritmo de inferência por trás de uma API pública já congelada em paridade com o R — exige sinal do coordenador (§8 do CLAUDE.md) antes de qualquer tentativa, para alinhar expectativa sobre a diferença numérica esperada entre a aproximação Python e o resultado original em R.

## 2026-08-12 — sus_climate_anomaly: verificação de "sem correspondência no join" é código morto

## 2026-08-12 — ⚠️ sus_climate_aggregate: Python e R têm o MESMO NOME mas fazem coisas DIFERENTES
- **Onde:** `climasus4py/enrichment/climate_aggregate.py::sus_climate_aggregate` vs. `climasus4r/R/sus_climate_aggregate.R`
- **O quê:** o R `sus_climate_aggregate(health_data, climate_data, climate_var, ...)` é um **joiner clima+saúde**: liga cada registro de saúde (`sus_spatial_join()`, com `date`/`code_muni`/`geom`) à estação climática mais próxima (`sus_climate_fill_inmet()`, com `date`/`station_code`/`latitude`/`longitude`) e cria colunas de defasagem/janela móvel (`lag*`, `mvwin*`). O Python `sus_climate_aggregate(rel, time_resolution, ...)` já portado é uma função **totalmente diferente**: agregação temporal pura de uma única fonte INMET (`monthly`/`seasonal`/`yearly`), sem join espacial, sem `health_data`, sem colunas de defasagem, retornando `time_bucket` em vez de `date`. Em vez de aproximar ou pular a função (ela é a base de 6 outras: `sus_mod_af`, `sus_mod_excess`, `sus_mod_metaregression`, `sus_mod_pool`, `sus_mod_sensitivity`, `sus_mod_swot`), a base spline natural, a cross-basis bidimensional e a grade de predição centrada com IC de Wald foram reimplementadas do zero em NumPy, com o algoritmo exato extraído do código-fonte real de `dlnm` 2.4.10 (`crossbasis`, `onebasis`, `crosspred`, `mkXpred`, `mkcen` — todos instalados localmente via R/`climasus4r` 1.0.0) e validadas numericamente: RR, IC, RR cumulativo por lag, dispersão, AIC e p-valor de Ljung-Box batem com uma saída real de `climasus4r::sus_mod_dlnm()` a menos de 1e-6, em um dataset sintético fixo pinado como teste de regressão (`tests/test_mod_dlnm.py`, fixture `tests/fixtures/dlnm_synthetic_input.csv`).
- **Nuance importante:** os coeficientes do GLM ajustado em Python **não são numericamente idênticos** aos do R — a base spline natural usa uma parametrização diferente (mas matematicamente equivalente, mesmo espaço de função, mesmos nós) da que `splines::ns()` produz via QR. Como o ajuste GLM é invariante a uma reparametrização linear de um bloco de colunas preditoras, os valores preditos/RR (o que realmente importa para paridade de comportamento) batem exatamente — só os coeficientes brutos (`fit["model"].params`) diferem se alguém comparar diretamente com `coef(fit$model)` do R.
- **Por que registrar mesmo validado:** é uma decisão de engenharia not-completely-mechanical (reimplementação de algoritmo estatístico, não tradução de sintaxe) — o coordenador deve estar consciente de que esta função não usa nenhuma biblioteca "de terceiros" para a matemática central do DLNM, e que qualquer mudança futura no algoritmo precisa reexecutar a validação numérica contra o R (script em `/tmp/dlnm_validate/`, não commitado — reproduzível a partir do R+dlnm+climasus4r instalados localmente).

## 2026-08-13 — sus_mod_af: bug de correctness silencioso confirmado no R (dlnm::crosspred desalinha RR por dia) — RECOMENDA-SE REPORTAR UPSTREAM AO climasus4r
- **Onde:** `climasus4r/R/sus_mod_af.R::.saf_component` (linha ~211, `dlnm::crosspred(cb, model, at = x, cen = cen)`); porte correto em `climasus4py/enrichment/mod_af.py`.
- **O quê:** `dlnm::crosspred()`, ao receber `at` como um vetor simples (não `NULL`, não matriz), executa `at <- sort(unique(at))` internamente (função `dlnm:::mkat`) antes de montar a grade de predição. O `allRRfit` retornado fica, portanto, em **ordem crescente de exposição**, com `names(allRRfit)` = os valores de exposição ordenados (como string). `.saf_component()` então faz `an_i <- cases * (1 - 1/rr_obs)` — uma multiplicação vetorial **posicional** (R não realinha por nome em `*` entre dois vetores simples) — pareando `cases[i]` (ordem cronológica/`data_daily`) com `rr_obs[i]` (ordem ordenada por exposição). Isso é **incorreto sempre que a série de exposição não é monotônica** (ou seja, para qualquer série climática real). Confirmado numericamente em `/tmp/af_validate/` (não commitado, reproduzível com R + `dlnm` + `climasus4r` instalados localmente): no dataset sintético de `tests/fixtures/dlnm_synthetic_input.csv`, FA total "como o R calcula" = -5,03%; FA total corrigido (realinhando `rr_obs` por nome antes da multiplicação) = -5,32%. O erro se propaga para TODOS os outputs de `sus_mod_af()`: `$total`, `$by_quantile`, `$daily`, `$by_period` — e, por extensão, para qualquer coisa que consuma esse objeto (`sus_mod_burden`, `tidy.climasus_af`, pooling entre cidades).
- **Classificação:** correctness silencioso (regra 4/§3.3 do CLAUDE.md) — resultado numericamente errado, sem qualquer aviso ao usuário, não um "quirk" de comportamento intencional. Por isso o Python **não replica** esse comportamento — `sus_mod_af()` em Python calcula o RR já alinhado à ordem de `data_daily` (nunca ordena/deduplica os pontos de predição), e foi validado a menos de 1e-6 contra o valor R CORRIGIDO (não contra o output bruto do R, que está errado).
- **Por que registrar mesmo corrigido:** 1) é uma divergência numérica real e documentada entre os pacotes R e Python sob o mesmo nome público — qualquer comparação direta com a saída atual do R vai "discordar" do Python, e isso precisa estar documentado para não ser confundido com um bug do port; 2) **recomenda-se fortemente reportar este achado como issue no repositório `climasus4r`** — é um bug real que afeta todos os usuários R do pacote, não só a paridade com Python; o coordenador deve decidir se/quando abrir a issue upstream.
- **Nota lateral (comportamento preservado, não um bug):** o método delta (`nsim=0`, usado quando `MASS` está indisponível no R) sempre reporta CI a 95% via o default do próprio `dlnm::crosspred()`, ignorando o `alpha` que o usuário passou para `sus_mod_af()` — isso É preservado no Python (`_DELTA_CI_LEVEL = 0.95` fixo nesse caminho), pois é um comportamento consistente e documentável, não um resultado silenciosamente incorreto.
